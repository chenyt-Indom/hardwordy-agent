### ③ `frontend/app.js`（6430 行）—— 本项目的"心脏"

**看哪里：第 3093 行 `async function doSend(...)`**，一路读到第 3900 行左右。

**这条主线要跟下来：**

```
用户点发送
  → send() 取输入、判空、判 streaming（第 3060 行附近，这里有个"卡住自愈"）
  → doSend() 建思考气泡 + 回答气泡
  → 判通道：_prov 是 deepseek* → /api/chat/deepseek，否则 /api/chat
  → reader.read() 循环：按 \n 切 NDJSON、逐行 JSON.parse
      · obj.message.content  → answer += ...  → paintAnswer()
      · obj.message.thinking → pushThinking()
      · obj.ping             → 只是心跳，重置看门狗
      · obj.__end            → answer = obj.answer（以服务端为准）+ 立刻重绘
  → 循环结束后：renderFinal(气泡, answer)   ← 第 1196 行
  → 回读服务端会话，比屏幕长就用它重绘
```

**顺带看三个函数（都不长）：**

| 行号 | 函数 | 作用 |
|---|---|---|
| 1182 | `isPlainMode()` | 纯文本 / markdown 的开关（默认 markdown，`?plain=1` 切纯文本） |
| 1196 | `renderFinal()` | 统一渲染入口，**渲染后逐字核对结尾，丢了就退回纯文本** |
| 1222 | `addMsg()` | 历史消息也走 `renderFinal`（早期只有实时消息走，导致"第二三条断"） |

**自测：** 为什么流式阶段用 `textContent` 而不是 `mdToHtml`？（提示：想 mdToHtml 遇到未闭合的 `**` 会怎样）

### ⑤ `backend/deepseek_client.py`（746 行）

**看哪里：第 355 行 `chat_stream_with_tools`**，这是全项目最值得读的函数，只有 300 多行。

## 附录 B · 五层"不丢字"是怎么叠起来的

| 层 | 位置 | 作用 |
|---|---|---|
| 1 | `deepseek_client` 的 `content_buf` | 生成侧完整，不受网络影响 |
| 2 | `main.py` 云端 `gen()` 的 `__end.answer` | 前端拿到整段原文，不靠分片拼 |
| 3 | 同上的 `sessions.save_messages` | 服务端自己落盘一份，独立于前端 |
| 4 | `session_save` 的"只许增长" | 前端丢片上传的短版本覆盖不掉长原文 |
| 5 | `renderFinal` 的尾部核对 + 前端回读 | 屏幕与原文逐字比对，缺了自动退回纯文本 |

**自测：** 把第 3 层去掉，什么场景会出问题？（提示：前端 PUT 发生在渲染之后）

## 附录 C · 常见"看起来像 bug"其实不是

| 现象 | 其实是 |
|---|---|
| 回答的 `innerText` 比日志里的字数少几十 | markdown 标记（`**`、反引号、`- `）不占可见字符 |
| 改了前端但界面没变 | WebView 缓存；现在脚本带 `?v=时间戳`，且顶栏有版本号可核对 |
| 日志里 `__end local=N server=N` 相等但屏幕短 | 渲染层；`renderFinal` 会核对尾部并退回纯文本 |
| 定时任务"没反应" | 一次要 60~120 秒，且后台跑；看任务卡片的 `last_run`，不是看按钮 |

## 阅读节奏建议

```
Day 1  上午：run.py + index.html            （打底，1 小时）
Day 1  下午：app.js 的 doSend 主线           （最费脑，慢慢来）
Day 1  晚上：main.py 两个端点 + __end        （对照前端看，会豁然开朗）
Day 2  上午：deepseek_client 全文            （300 行，值得逐行）
Day 2  下午：tools.py 挑 5 个 _do_ 函数      （不用全读）
Day 3  上午：selfdev + keyvault + scheduler  （三个小文件）
Day 3  下午：自己动手改一个小功能，跑通       （这一步才算"吃透"）
```

**最后一条建议：** 读完不要立刻合上，去改一个小东西——比如把"发送"按钮的文案改掉，或给某个工具加一行日志。**能改通，才算读懂。**
